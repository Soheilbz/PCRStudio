# Platform backend

Django owns verified email accounts, personal and organization memberships, and explicit project access. All scientific execution remains outside this runtime. Custom UUID users are defined in migration one; PostgreSQL is the only supported database.

Run tooling through the project's Docker tools container and `./bootstrap check deep`. Direct tools commands are `python manage.py migrate --noinput`, `pytest tests`, `python manage.py spectacular --file openapi.json --format openapi-json --validate --fail-on-warn`, `ruff check .`, `ruff format --check .`, `mypy .`, and `bandit -q -r . -c pyproject.toml`. Runtime uses Gunicorn with access logging disabled; safe application logging emits generated request IDs, static route templates, method, status, bounded error category and elapsed time. Request paths, query strings, bodies, headers, names, emails and exception traces are omitted.

Required private secrets: `DJANGO_SECRET_KEY[_FILE]`, `MFA_ENCRYPTION_KEY[_FILE]` (a separately generated Fernet key), and `POSTGRES_PASSWORD[_FILE]`. The MFA key encrypts allauth TOTP and recovery-code secrets independently from the cookie/session signing key. Preserve it with database backups. Rotating `DJANGO_SECRET_KEY` invalidates existing sessions without damaging MFA enrollment. MFA encryption key rotation requires a controlled re-encryption migration under exclusive maintenance with both keys available, validated restoration and no secrets in logs. Replacing the MFA key without re-encrypting existing records prevents users from authenticating; never do so as an ordinary bootstrap action.

Other configuration: `PGHOST`, `PGPORT`, `PGDATABASE`, `PGUSER`, optional PostgreSQL `DATABASE_URL`, private `VALKEY_URL`, `FRONTEND_URL`, `DJANGO_ALLOWED_HOSTS`, `CSRF_TRUSTED_ORIGINS`, and SMTP settings. Local HTTP requires insecure cookies only for the isolated loopback environment. Set `FRONTEND_URL` to HTTPS for secure cookies and HSTS. Only the sanitizing Caddy proxy reaches the API; the authentication limiter trusts its forwarded client IP and stores a secret-salted digest. Test tooling uses a separate Valkey database and a PostgreSQL identity permitted to create isolated test databases.

Dependency resolution uses the named Aliyun PyPI artifact mirror because the primary PyPI artifact CDN is unreachable in this execution environment. Package versions and every locked artifact digest must be independently verified against official PyPI release JSON by the project provenance checker. Lockfile hashes remain mandatory. The mirror does not define package authority or justify ignoring security findings.

All `/api/v1/` writes use session cookies and CSRF. `GET /api/v1/csrf/` bootstraps an anonymous CSRF token. allauth owns browser identity flows at `/_allauth/browser/v1/`, including verification, password reset, TOTP, recovery codes and session management. Operators and current organization owners require both TOTP enrollment and an actual MFA authentication record in the current session for platform access and cannot disable their required factor. Password-only sessions do not gain factor strength after enrollment or role promotion. Creating an organization also requires current factor proof. `GET /api/v1/me/` exposes neutral enrollment/authentication state so Account remains available for setup and reauthentication without workspace access. Recovery additionally requires factor authentication within five minutes and an enumerated operational reason.

Existing-TOTP accounts also require recent native MFA confirmation for reading/regenerating recovery codes and credential changes. The provider's recent-password check alone does not satisfy factor strength. Initial enrollment and the native MFA confirmation endpoint remain reachable. The UI confirms the enrollment code through that native endpoint before reading codes and always refreshes identity after successful enrollment, even if a later retrieval fails.

Organization ownership does not grant project content access. Memberships are irrevocable identities: removal never reactivates a row, and rejoining creates a new row. Existing grants therefore remain revoked. Sensitive mutations lock the workspace before the project and recheck current permission inside the transaction, together with an opaque audit event. Stale project versions return `409 version_conflict`. Organization orphan discovery returns only project IDs and versions. Recovery returns this same neutral shape and grants ownership only to the explicitly selected active membership.

Invitation and recovery notifications are sent after the domain transaction commits. SMTP transport failures preserve the successful mutation and emit a fixed `notification_failed` event containing only the operational notification kind. This foundation has no durable notification queue or automatic delivery retry.
